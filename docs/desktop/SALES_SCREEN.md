# Ventes: the cash checkout screen

The Ventes (Sales) entry in the sidebar opens `SalesPanel`. The cashier searches for a variant,
builds a basket, confirms the cash, and the sale is saved offline by `SaleService`, which also
removes the stock in the same database transaction. The screen never calls `StockService.adjust`.

## Using it

1. Type in the search box. Every word must match the name, internal reference, family, model,
   category or characteristics, ignoring case and accents. Only variants are listed, never a family.
2. Press Enter or click **Add to basket**. Up and Down choose another result while you type. Adding
   the same variant again adds one more unit to its line.
3. Click a quantity, or select the line and type, then press Enter. Delete or **Remove line** removes
   a line. Pieces and bags must be whole; kg and litres accept three decimals, with a comma or a dot.
4. Click **Take cash payment**, then **Yes, cash received**.

The saved receipt reference and total appear after the sale, and the stock column is read again.
Buying prices are never shown: a basket line does not even contain one.

## Exact amounts

Quantities are whole thousandths in a `long` (1000 = 1 piece, bag, kg or litre), parsed with
`BigDecimal`, never floating point. Each line is rounded to whole FCFA with exact halves going up,
then the rounded lines are added with overflow checks. This is the same calculation as `SaleService`,
and `CheckoutTest` checks that the two agree. After a sale, the screen shows the saved totals.

## How a sale stays safe

`Checkout` follows one rule: save the details first, send second, forget them only once the answer
is certain.

| What happens | What the cashier sees | Saved file |
| --- | --- | --- |
| The sale is saved | Receipt and total; the basket empties | Removed |
| Not enough stock, or the sale is refused | The reason; the basket stays and can be changed | Removed |
| The details cannot be written to disk | Nothing was sent; the basket stays | None |
| Any other failure: no certain answer | The basket locks; **Try again** or **Cancel this sale** | Kept |
| Cella closes during a sale | At the next opening: the same locked basket and choice | Kept |
| The file cannot be read | New sales are blocked; **Set the file aside** | Left untouched |

- **Try again** sends the same sale ID, receipt, device, lines and prices. `SaleService` recognises a
  repeat and returns the saved sale, so a second sale or a second stock deduction cannot happen.
- **Cancel this sale** first checks the database. If the sale was really saved, it is reported as saved.
- Opening the screen reads the database and the file, but it never sends anything by itself.
- **Set the file aside** renames the file to `pending-checkout-damaged-<time>.txt`. Nothing is deleted.
  Refresh also notices a file that someone fixed or moved by hand.

One basket keeps one sale ID. After a refusal, the same basket reuses its ID; a changed basket gets a
new one, which is safe because the old ID was never saved.

Each sale sends its unit prices explicitly. `customUnitPrice` is used only to freeze the price the
customer was told, so a retry can never charge a different amount. No screen can type a custom price,
and discounts and tax are not part of this milestone.

## Receipt references

The format is `REC-<yyyyMMdd>-<12 hexadecimal characters of the sale ID>`, for example
`REC-20261105-C527DE5980E6`. The database does not force receipts to be unique, so the reference uses
48 random bits. There is no counter, so a restart or a second computer cannot repeat a number by
counting from the same place.

## The pending file: `pending-checkout.txt`

It sits in the data folder, next to `cella.db`, and normally exists only while a sale is being sent.
It is a Java properties file in UTF-8, written to `pending-checkout.txt.tmp`, forced to disk, then
moved over the real file in one step, so a power cut never leaves half a file.

```properties
format=1
saleId=<UUID>
shopId=<UUID>
deviceId=<UUID>
receiptNumber=REC-20261105-C527DE5980E6
lineCount=1
line.0.productId=<UUID>
line.0.label=Riz - Basmati, sac de 25 kg
line.0.reference=P-0001
line.0.unit=bag
line.0.quantityMilli=2000
line.0.unitPrice=28000
```

Do not edit this file. A wrong format, a missing value, an impossible quantity or a shop ID that is not
this shop's all count as damage. A future format must use a new `format` number.

## Known limitations

- The history reads every sale of the shop each time it opens, because the service has no paging. This suits the pilot; a shop with years of sales will need paging.
- A basket keeps the price from when the line was added. Core has no product edit yet, so a price
  cannot change while a basket is open. When an edit screen arrives, this needs another look.
- Checkout recovery is coordinated across copies of Cella using the same local data folder:
  a JVM-local lock plus an OS file lease covers recovery, submission and confirmation.
  A competing active checkout is blocked; a different pending request cannot be overwritten.
  This is local-filesystem coordination, not multi-device/cloud synchronization.
- Stock in the screen is guidance. The database makes the final decision when the sale is saved.
- No void, receipt printing, Mobile Money, credit, discount, tax, login or sync, by design.

reads products and stock again each time it is opened.


## Sales history

**Historique des ventes** at the top of Ventes opens the saved sales of this shop. **Retour à la caisse**
returns to the checkout. Both are pages of the same `SalesPanel`, so going there only swaps what is shown:
the basket, a waiting cash confirmation and an unfinished sale stay exactly as they were.

- **It only reads.** `SalesHistoryPanel` calls `SaleService.listSaleStates` in a background thread. It never
  changes a sale, the stock or `pending-checkout.txt`.
- **Effective status.** Each row shows Payée or Annulée in words, from `SaleState`. A cancelled sale keeps its row.
- **Order.** Newest first; two sales saved at the same instant are ordered by their ID, so the order never
  changes between reads. The sort works on a copy of what the service returned.
- **Filters.** Any part of the receipt, ignoring case; all, paid or cancelled; and an optional range of days
  written `jj/mm/aaaa`, both days included. The filters stay in place when the page is left and opened again.
- **Time zone.** Saved times stay in UTC. They are displayed in Africa/Douala by `CatalogStyle.localDateTime`, and
  the day filters use the same zone: a Douala day starts at 23:00 UTC on the day before.
- **What replaces the table when there is no row:** loading, no sale saved yet, no sale matching the filters,
  a wrong date, or a failed read with **Réessayer**. A failed read says that it does not mean there are no
  sales, and it removes the old rows rather than leaving them looking current.
- **Newest read wins.** Each read has a number, and an older read that finishes late is ignored.
- **While a sale is being saved** the history button is disabled. If a sale is unfinished or its file is damaged,
  the history can still be opened, and a warning says the sale is still waiting at the checkout.
- **A quantity still being typed** is finished first, as when clicking anywhere else. If it is refused, the
  line keeps its previous quantity and the reason stays on the basket.

## Receipt details (OFF-01)

Select a sale in the history, then click **Ouvrir le reçu →**, press Enter, or double-click it. Typing part of
a receipt in the search box then pressing Enter also opens the selected sale; Enter in an empty search box
opens nothing. **← Retour à l’historique** or Escape returns to the list with the same search, status,
dates and selected sale, and **Retour à la caisse** from there finds the basket as it was.

- **Only saved values.** The receipt, date and time (Africa/Douala), payment, status, and each line's
  product name, reference (such as `P-0001`), quantity in its unit, charged unit price and line total all
  come from the saved sale. The total is the saved total. Nothing is looked up in today's catalogue or
  calculated again, so a later price, name or reference change never alters an old receipt. A saved sale
  has no buying price, so none can appear.
- **References of older sales.** Each sale line has saved its product's reference since schema 9. Lines
  saved before took their product's reference during the upgrade; shop references are never edited, so it is
  the reference the product had when it was sold.
- **Cancelled sales** say Annulée, with a notice giving the cancellation date and the reason exactly as it
  was recorded. The original lines and total stay on the page.
- **It only reads.** The receipt uses the sale already read for the list, so opening it makes no new
  database call and writes nothing.
- **Reads while it is open.** If the history is read again while a receipt is open, for example when you
  come back to Ventes from another screen, the receipt shows the newer read of the same sale, such as a
  cancellation made meanwhile. If that read
  fails, the receipt stays on screen, and the list shows the failure on the way back.

## Review correction — pending checkout ownership

Charles's original commits (through `a99b36f`) are retained. Follow-up fixes add
CheckoutFileLease: a per-path JVM lock plus an OS file lock on
`pending-checkout.txt.lock`. Lease acquisition is nonblocking; another active
writer shows a translated recovery message rather than freezing Swing. File and
SQLite calls remain off the EDT. Keep the lock file in place while Cella runs.
Nested store operations reuse the current thread's lease.

The lease covers the complete Checkout operation, including the database check,
send and recovery-file cleanup. Saves use uniquely named temporary files and
refuse to replace an existing different request. Identical pending saves are a
no-op. Retry/discard verify the original request first; cleanup uses an expected
sale ID, so a stale window cannot remove a newer pending checkout. Replaying an
already saved sale without a pending file reads its saved record without sending
an untracked request. A readable valid request cannot be moved aside by a stale
“damaged file” action.

A second window may preserve an unsent basket while another sale is unresolved.
Refresh checks recovery again. Database idempotency and file ownership work
together: no window is allowed to erase the identity needed for safe restart.
Corrupt/unavailable storage remains blocked for recovery. A failed recovery-file
write never submits a new sale.

Regression coverage includes conflicting pending saves, stale clear/discard,
active submissions across service instances, a separate JVM holding the OS lock,
restart/response-loss paths and storage becoming unavailable after opening Sales.
Original single-sale, quantity, rounding, search and GUI integration tests remain.
Real Windows GUI testing is still separate from these headless checks.
